## 2. Per-Issue SA

### ISSUE-001: buildExecRequest stale ResetSession message

**現狀：** `Net10HostBackend.fs:98` 回傳 `Error "ResetSession is not implemented for Net10HostBackend yet."` 但 `IFsiExecutionBackend.ResetSession` 已在 line 167-201 完整實作。

**影響範圍：**
- `Execute` method (line 134-158) 經 `buildExecRequest` dispatch
- 若 caller 透過 `Execute` 路徑傳入 `ResetSession` OperationKind，會收到誤導的 `UnsupportedOperationException`
- 實際上 `reset_fsi_session_routed` tool 走的是 `McpExecutionTools.ResetFsiSessionRouted` → `FsiMcpService.ExecuteOperation(ResetSession, ...)` 路徑

**修改範圍：** 僅 1 行，改 error message
**風險：** 極低

### ISSUE-002: SessionFaulted 無自動恢復

**現狀：** `ExecutionRouter.fs:39-43`，任何 `record.Result.IsSuccess = false` 都將 session 標為 `SessionFaulted`。

**影響範圍：**
- 所有經 `RouteAndExecute` 的執行（所有 routed tools）
- 語法錯誤、runtime exception、timeout 都會觸發
- 一旦 faulted，upstream FSI supervisor 回 "Operation could not be completed due to earlier error"
- 後續所有操作全部失敗，agent 無法自救

**修改方案分析：**

| 方案 | 描述 | 優劣 |
|------|------|------|
| A: 不標 Faulted | 移除 SessionFaulted 標記，永遠用 backend 回報的狀態 | 最簡單，但可能掩蓋真正的 fatal error |
| B: 區分 fatal/non-fatal | 根據 RawErrorType 判斷是否 fatal | 較精確，但需要知道所有 error type |
| C: 自動 reset | 執行前若 Faulted 則自動 reset | 最佳 UX，但 reset 有副作用（清除 session state） |
| **D: 用 backend 狀態 + 錯誤提示** | 不覆寫為 Faulted，用 backend 實際狀態；若 backend 報 Faulted，在 error 中附加恢復指引 | **推薦** — 最小侵入，正確反映實際狀態 |

**推薦方案 D：**
- `ExecutionRouter.RouteAndExecute` 中，永遠用 `backendSession.Status`（從 `backend.GetSessionState` 取得），不自行覆寫為 `SessionFaulted`
- 若 `backendSession.Status = SessionFaulted`，在 error output 附加恢復提示
- 這樣 non-fatal error（語法錯誤等）不會 poison session
- 真正的 FSI faulted 狀態由 backend 如實回報

**風險：** 中等 — 行為變更，但是修正了一個 bug（non-fatal error 不應 fault session）

### ISSUE-003: 模糊錯誤訊息無上下文

**現狀：** upstream FAkka.FSI.Supervisor 回 "Operation could not be completed due to earlier error"，MCP server 原樣傳遞。

**影響範圍：**
- `McpExecutionTools.formatResultError` (line 25-29) 是所有 routed tool 的 error formatter
- 目前只回傳 `result.Errors` 或 fallback message

**修改方案：**
- 在 `formatResultError` 中偵測此特定錯誤訊息
- 補充 session recovery hint
- 與 ISSUE-006 合併處理（都是 error context enrichment）

**風險：** 低

### ISSUE-004: invalidOp 用於業務邏輯

**現狀：** 5 處使用 `invalidOp` 處理「host not found」、「unsupported host kind」等正常業務情境。

**影響範圍：**
| 位置 | 訊息 |
|------|------|
| Net10HostBackend.fs:33 | `"Host '{hostId}' was not found."` |
| ExecutionRouter.fs:29 | `"Host '{request.Route.HostId}' was not found."` |
| McpFsiTools.fs 多處 | `"Host '{route.HostId}' was not found."` |
| McpControlPlaneTools.fs:21 | `"create_fsi_host does not support inproc."` |
| McpResultTools.fs:38 | `"Unsupported result query kind '{other}'."` |

**修改方案：**
- MCP tool 層（McpControlPlaneTools、McpResultTools、McpExecutionTools）：改為直接 return error string（這些 method 回傳 `Task<string>`，exception 會被 MCP SDK catch 並轉為 error response，但 stack trace 是多餘的噪音）
- Backend/Router 層（Net10HostBackend、ExecutionRouter）：改為 return descriptive error string（同理，最終都是 MCP tool 消費）
- 不引入新的 DU type — 目前 codebase 風格是 string error，引入 Result<T,McpError> 需要大量重構，超出本輪修復範圍

**風險：** 低 — 只改錯誤回報方式，不改正常路徑

### ISSUE-005: Console.WriteLine in service methods

**現狀：** `McpFsiTools.fs` 有 16 處 `Console.WriteLine` 在 service 方法中。

**影響範圍：**
- MCP 協議 stdout 干擾（MCP spec 要求 logging 走 stderr）
- 但實際上這些 Console.WriteLine 是 debug logging，MCP server 本身使用 HTTP transport（非 stdio），所以 stdout 不會直接干擾 MCP protocol
- 仍然應該清理 — 正式服務不應用 Console.WriteLine

**修改方案：**
- 全部移除（這些是 debug tracing，不是 user-facing output）
- 不改為 ILogger — 目前 McpFsiToolsType 是 static class，注入 ILogger 需要架構變更，超出本輪範圍
- 若需保留 tracing，改用 `Console.Error.WriteLine`（stderr，不干擾 stdout MCP）

**推薦：** 直接移除。FSI execution 的輸入輸出已經透過 `FsiExecutionRecord` 完整記錄在 result registry 中。

**風險：** 極低

### ISSUE-006: 錯誤回傳缺乏執行上下文

**現狀：** `McpExecutionTools.formatResultError` 只回傳 `result.Errors` 或 fallback message。

**影響範圍：** 所有 6 個 routed tool 的 error path。

**修改方案：**
- 不改 `formatResultError` 簽名（它沒有 record context）
- 改在每個 tool method 的 error path 中，直接組合 error + context
- 或：改 `formatResultError` 為接受 `FsiExecutionRecord` 的 overload

**推薦：** 新增一個 `formatRecordError` helper，接受 `FsiExecutionRecord`，組合：
```
{errors}\n[RequestId={requestId}, HostId={hostId}, SessionId={sessionId}, Backend={backendKind}]
```

**與 ISSUE-003 合併：** 若偵測到 "Operation could not be completed due to earlier error"，額外附加 recovery hint。

**風險：** 低

### ISSUE-007: failwith in async queue

**現狀：** `McpFsiTools.fs:747` 在 channel write 失敗後 `failwith`。

**影響範圍：**
- `EnqueueExecuteCode` method，由 `execute_f_sharp_code_async` 和 `execute_f_sharp_code_async_routed` 呼叫
- failwith 拋出 `System.Exception`，MCP SDK 會 catch 並回傳 error response
- 但在 failwith 之前（line 741-746）已經呼叫了 `asyncJobRegistry.Fail`，所以 asyncId 已標為 failed
- 問題是 failwith 後的 stack trace 沒有價值

**修改方案：** 直接 return error string（`EnqueueExecuteCode` 回傳 `string`）而非 throw

**風險：** 低

### ISSUE-008: case-sensitive enum 缺文件

**現狀：**
- `parseLanguage`: 接受 `"fsharp"` / `"fsharpcode"` → FSharpCode，其他 → BuiltIn（靜默 fallback）
- `parseKind`: 只接受 7 個小寫值，其他 → `invalidOp`（無列出有效值）
- `parseHostKind`: 有 `ToLowerInvariant` 但錯誤訊息不完整

**修改方案：**
- `parseKind` invalidOp message 列出所有有效值
- `parseLanguage` 在 fallback 前檢查是否為常見拼錯（如 `"FSharp"` → 也接受）
- `parseHostKind` 錯誤訊息已列出有效值，但 `"inproc"` 的 error 需要加 guidance
- Tool description 中補充有效值（已在 ISSUE-017 覆蓋，但 P1 scope 先處理 error message）

**風險：** 極低

### ISSUE-009: ProvisioningServices polling 無 max-retries

**現狀：** `ProvisioningServices.fs:71-89` `pollProcSnapshot` 使用 `deadlineUtc` 做 timeout，每次 delay 250ms。

**影響範圍：**
- `CreateHost` 中有兩處呼叫 `pollProcSnapshot`，deadline 都是 `DateTime.UtcNow.AddSeconds 15.0`
- 理論上最多 60 次 poll（15s / 250ms）
- 實際風險：若 `tryGetProcSnapshot` 本身很快返回，250ms delay 確實保護了 polling 頻率
- 但 `Task.Delay 250` 後的遞迴沒有 depth limit

**修改方案：** 加入 `maxAttempts` 參數，預設 60（15s / 250ms），作為額外保護。

**風險：** 極低
