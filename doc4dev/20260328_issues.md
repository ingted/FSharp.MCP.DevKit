### ISSUE-001: Net10HostBackend.buildExecRequest 錯誤地攔截 ResetSession

**檔案：** `src/FSharp.MCP.DevKit.Server/Backends/Net10HostBackend.fs:98`

**現象：**
`buildExecRequest` 中 `ResetSession` case 回傳 `Error "ResetSession is not implemented for Net10HostBackend yet."`，但 `IFsiExecutionBackend.ResetSession` 方法（同檔案 line 167-201）**已經完整實作**。

**影響：**
- 透過 `Execute` dispatch 路徑觸發的 reset 操作會被誤攔
- Agent 呼叫 `reset_fsi_session_routed` 時可能收到 `UnsupportedOperationException`
- 但實際上 ResetSession 功能是可用的

**根因：** `buildExecRequest` 本來只處理需要轉換為 `FsiSupervisorExecRequest` 的操作。ResetSession/GetState/RestartHost 走不同的 method，不應出現在 buildExecRequest 中。但目前 error message 暗示「尚未實作」，這是殘留的 stale message。

**建議修復：**
1. 將 error message 改為 `"ResetSession is dispatched via IFsiExecutionBackend.ResetSession, not Execute."` 以免誤導
2. 或者直接在 `Execute` 中對 `ResetSession` OperationKind 做 redirect，呼叫 `this.ResetSession(request.Route)`

**NOTE (2026-03-28 update):**
- 已修正錯誤訊息，且 routed `GetState/ResetSession/RestartHost` 現在已改為 direct dispatch，不再依賴 `Execute` 假路徑。
- 現況在 `Net10HostBackend.buildExecRequest` 中為：
  - `GetState -> "GetState is dispatched via IFsiExecutionBackend.GetSessionState, not through Execute."`
  - `ResetSession -> "ResetSession is dispatched via IFsiExecutionBackend.ResetSession, not through Execute."`
- 此 issue 已解。

### ISSUE-002: Session Faulted 無自動恢復，後續操作全部失敗

**檔案：** `src/FSharp.MCP.DevKit.Server/ControlPlane/ExecutionRouter.fs:39-43`

**現象：**
```fsharp
Status =
    if record.Result.IsSuccess then
        backendSession.Status
    else
        SessionFaulted
```

任何一次執行失敗都會將 session 標記為 `SessionFaulted`。之後 upstream FSI supervisor 回傳 `"Operation could not be completed due to earlier error"` 這個極度模糊的錯誤訊息。

**影響：**
- Agent 完全無法得知是哪個操作導致 faulted
- 後續所有操作都失敗，即使新的程式碼本身沒有問題
- Agent 必須知道要建立新 session 才能恢復

**根因：** FSI session 內部的 error state 是 sticky 的（一旦 FsiCompilationException 就永久 faulted），但 MCP server 沒有嘗試自動恢復或提供清晰的指引。

**建議修復：**
1. 在 `RouteAndExecute` 中，若 backend 回報非致命錯誤（如語法錯誤），不標記為 `SessionFaulted`
2. 或在執行前檢查 session 狀態，若為 Faulted 則自動嘗試 reset
3. 至少在錯誤回傳中包含 `"Session is in Faulted state. Create a new session or call reset_fsi_session_routed to recover."`

**NOTE (2026-03-28 update):**
- 這個根因目前仍存在，尚未做自動恢復，也未改 upstream sticky fault 模型。
- 但 server 端現在已加入 faulted session 前置攔截與錯誤補強：
  - routed execution 失敗時會附帶 `RequestId/HostId/SessionId/Backend/ResultId`
  - 若 session registry 已知為 `SessionFaulted`，server 會直接回明確錯誤，不再等 upstream 回 `"Operation could not be completed due to earlier error"`
  - 會附 recovery hint，提示使用 `reset_fsi_session_routed` 或建立新 session
- 此 issue狀態：已降低主要可用性痛點，但未根治 faulted session 自動恢復問題。

### ISSUE-003: 「Operation could not be completed due to earlier error」錯誤訊息無上下文

**來源：** 上游 FAkka.FSI.Supervisor 套件（非本 repo 程式碼）

**現象：** 當 FSI session 在 Faulted state 下收到新的執行請求，回傳此通用錯誤。

**影響：** Agent 無法判斷：
- 是哪個 session 出問題
- 是什麼原因導致 faulted
- 該如何恢復

**建議修復：**
1. 在 MCP server 層攔截此錯誤，補充 RequestId、HostId、SessionId、上一次失敗的 ResultId
2. 在回傳訊息中附加 `"Hint: The session entered Faulted state after a previous execution failure. Create a new session with create_fsi_session or call reset_fsi_session_routed."`

**NOTE (2026-03-28 update):**
- 已修正主要痛點。
- `McpExecutionTools.formatRecordError` 現在會附：
  - `RequestId`
  - `HostId`
  - `SessionId`
  - `Backend`
  - `ResultId`
- faulted 類型訊息也會補 recovery hint。
- server 端對已知 faulted session 會直接產生具上下文的新錯誤，不再把 upstream 模糊字串原樣外漏成唯一訊息。
- 但 upstream `FAkka.FSI.Supervisor` 的原始錯誤字串仍然模糊，server 端目前是補上下文，不是改 upstream message 本體。

- channel write 失敗時會：
  - 將 async job 標成 failed
  - 寫入結構化失敗結果
  - 回傳字串錯誤訊息
- 不再 `failwith`。
- 此 issue 已解。

### ISSUE-017: Remote host 看到的檔案路徑與 agent container 路徑不同，導致 `#I` / `#r` 找不到非 NuGet DLL

**來源：** 2026-03-28 實際 agent 使用與 live MCP 重現

**現象：**
- agent 容器內常用的絕對路徑如：
  - `/workspace/home/work/...`
- 在部署中的 `fsharp-devkit` container 內未必存在。
- 例如目標腳本第 1~76 行原樣送入 remote session 時，會失敗於：
  - search path 不存在
  - `DynamicObj.dll` 等非 NuGet DLL 無法解析

**根因：**
- `gemini4` container 與 `fsharp-devkit` container 透過 host volume 掛載共享檔案，但容器內路徑不一定相同。
- remote host/process 真正執行 `#I` / `#r` 時，看的是 `fsharp-devkit` container 內可見路徑，而不是 agent 自己容器內的路徑。

**影響：**
- agent 會誤判成 remote host/session 壞掉
- 實際上只是路徑映射與 Runbook 指引不足

**目前判定：**
- 這主要是文件/agent 指引問題，不是 core runtime capability failure。
- live 驗證已證明：把 `#I` 改成 remote container 真可見的路徑後，相關 DLL 載入可成功。
- NOTE (2026-03-28 update):
  - 這個 issue 仍成立，但性質已明確收斂為 Runbook / agent 指引缺口。
  - 不能再把它誤判成 remote host/session runtime 壞掉。
  - `doc/Runbook.md` 需明寫 `/workspace/home/... -> /gemini4/...` 這類 deployed mapping 範例。

**建議修復：**
1. 在 `Runbook.md` 明寫 container-to-host-to-container 的 volume 對應
2. agent 執行前先確認 remote host 可見路徑，再產生 `#I` / `#r`
3. 對常見部署提供固定 mount 範例，例如 `/gemini4/...`

### ISSUE-019: 長時間 sync routed remote execute 在 live deployment 仍可能 timeout / disassociate

**來源：** 2026-03-28 實際 agent 使用與 live MCP 重現

**現象：**
- remote host / session 本身可建立且可用
- 路徑映射修正後，長腳本仍可能在：
  - `execute_f_sharp_code_routed`
  - `McpClientSystem <-> fsi-proc`
  這段同步 ask 路徑上出現：
  - `AskTimeoutException`
  - `EndpointDisassociatedException`

**已確認不是：**
- volume path mismatch
- `proc-supervisor` 不通
- `fsi-supervisor` actor path 不存在
- remote host/session 隔離能力不存在

**已確認較健康的替代路徑：**
- `execute_f_sharp_code_async_routed`
- 輪詢 `fsi/async/{asyncId}`
- 完成後再 `evaluate_f_sharp_expression_routed`

**影響：**
- agent 若直接用 sync routed execute 跑真實業務腳本，容易誤判整個 remote host/session 系統不穩

**建議修復：**
1. 在 `Runbook.md` 明寫長腳本一律先 async
2. 保留此 issue 為產品層 open issue，直到 sync routed execute 對長 workload 也穩定

**NOTE (2026-03-30 update):**
- 已找到本案主要根因，不是 Akka timeout/passivation，也不是 MCP async registry。
- 關鍵點在 `FAkka.FSI.Supervisor/FsiWorkerActor`：第一個 `ExecCode` 先在 actor thread 內同步 `EnsureSession(...)`，導致真實 heavy init 案例卡在錯誤執行路徑。
- 修正後改由 long-running execution task 內建立/確保 session，`mod2` fresh-image E2E 已可直接完成：
  - 分次 `execute_f_sharp_code_routed` 執行目標腳本 1..76 行
  - 後續成功 `evaluate_f_sharp_expression_routed`
  - 取回 `cfar.Cfarta....c`
- 這表示本 issue 對 `CFar` 案例已不再 blocking；保留條目是為了追蹤其他尚未覆蓋的長 workload sync routed execute。
