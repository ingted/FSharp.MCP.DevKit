# 20260320 Issues Observed From Agent / MCP Client Perspective

## Context

這份文件整理的是：在 `agent -> MCP client -> fsharp-devkit MCP server -> FSI session` 這條鏈上，從 **agent / MCP client 使用者** 的角度，實際遇到的問題。

素材來源有兩個：

1. 本輪真實使用 `fsharp-devkit` 的經驗
2. [00015.txt](/workspace/home/work/coldfar-symbolics/notes/00015.txt) 內的操作紀錄

目標不是討論業務程式，而是整理 **tooling / protocol / diagnostics / session model** 哪裡讓 agent 很難穩定、自主地工作。

## 1. `execute_f_sharp_code_async` 失敗時，常常沒有足夠診斷資訊

### 問題描述

`execute_f_sharp_code_async` 是這輪最重要、也最有價值的功能，因為它能避開同步 tool call timeout。

但它有一個非常致命的缺點：**失敗時常只回 `IsSuccess=false`，而 `Output=""`、`Errors=""`**，導致 agent 無法直接知道是：

- 某個 `#r` 沒成功
- 某個 `open` 找不到
- 某個 block 的 dependency 順序不對
- 還是 script directive 本身在 async path 有特殊限制

### 實際範例

本輪曾送一個包含多個 `#r`、`open` 的 block，回來的 status 類似：

```json
{
  "IsCompleted": true,
  "Result": {
    "Output": "",
    "Errors": "",
    "IsSuccess": false
  }
}
```

這時 agent 沒有辦法直接知道錯在哪，只能退回到「一個 assembly、一個 `open` 一個一個試」。

最後是靠拆解之後才定位到：

- `open FAkka.TA` 在那個 session 裡其實還缺 `MdcFsClient90.dll`

也就是說，**真正的問題存在，但 async 結果沒有把它講出來**。

### 影響

- agent 必須做很多低價值 bisect
- token / tool call 次數被浪費在「猜錯誤」而不是解問題
- 很難做自動恢復與重試策略

### 建議

1. `Result.Errors` 應盡可能保留 F# compiler / FSI 的原始錯誤內容。
2. 至少回傳第一個錯誤的檔案、行號、訊息。
3. 若 async path 對某些 directive 有限制，也應明確寫入 `Errors`，而不是只回 `IsSuccess=false`。

## 2. 同步工具容易卡 transport timeout，而 async 覆蓋面還不夠完整

### 問題描述

從 agent 端看，像這些操作其實都可能不是「瞬間完成」：

- `restart_fsi_session`
- `load_f_sharp_script`
- `reference_assembly`
- `add_search_path`

一旦這些操作稍慢，就很容易撞到外層 MCP tool call / client runtime timeout。

### 實際範例

本輪我們最後能穩定初始化 `cfar`，靠的是這個模式：

1. 用 async 逐步建立 session state
2. 最後單獨 async 跑 `let cfar = CFar(...)`
3. 用 `fsi/async/{asyncId}` resource 輪詢直到完成

而不是依賴同步工具一次做完。

[00015.txt](/workspace/home/work/coldfar-symbolics/notes/00015.txt) 也呈現出同樣的操作型態：

> 我分三個 block 送：#r/#open、helper 定義、let cfar = ...。前兩個很快回，最後一個只做 async 初始化，不再混別的東西。

這代表從實務上看，**長一點的動作需要 async-first 的設計**。

### 影響

- agent 很難對同步工具建立穩定預期
- 即使 server 端沒壞，client 也可能因為外層 timeout 誤判為 tool 不可用
- 對 agent 而言，tool 是否可靠常常取決於 transport timeout，不是取決於 F# 執行本身

### 建議

1. 為所有可能超過數秒的工具提供 async 版本。
2. 同步版本至少應保證「快速 ack + 明確告知改用 async」。
3. 若已有 async 對應版，文件應直接標示「這個操作建議預設用 async」。

## 3. Session model 對 client 幾乎是隱性的，不利於 agent 穩定工作

### 問題描述

`fsharp-devkit` 背後有 FSI session，這是很正確的設計；但從 client 角度，session 狀態目前太隱性。

agent 很需要知道：

- 我現在是不是同一個 FSI session？
- 這個 session 何時建立？
- 已經 `#r` 過哪些 assembly？
- include/search path 是什麼？
- 上一次 reset / restart 是什麼時候？

目前這些都缺乏直接可查的 API。

### 實際範例

本輪的工作流是：

1. 先把 `PersistedConcurrentSortedList.dll`
2. 再把 `SharFTrade.Exp.2025.dll`
3. 再把 `Plotly.NET.dll` / `FAkka.Shared.dll` / `Skender.Stock.Indicators.dll` / `MdcFsClient90.dll`
4. 再送 helper block
5. 最後 async 初始化 `cfar`

這整條鏈是否還在、是否已被重置，對 agent 非常重要。  
但目前 client 只能靠「再送一段 probe code 試試看」。

### 影響

- agent 很難做 deterministic workflow
- session 被重置或污染後，恢復成本高
- tool call 的成功 / 失敗，會依賴「前一輪到底做了什麼」，但沒有官方可讀狀態

### 建議

新增一個類似 `get_fsi_session_info` 的能力，至少回傳：

- session id
- session start time
- loaded assemblies
- search paths
- last reset time
- recent commands count

## 4. async tool 的回傳格式過於精簡，缺乏結構化 metadata

### 問題描述

`execute_f_sharp_code_async` 目前回傳的是一個 **bare string async id**。  
例如：

```text
8522769ee1104591a79ff3b3091777c6
```

這固然能用，但對 agent/client 其實不夠友好。

### 問題點

目前 client 需要自己假設：

- 這個字串就是 async id
- 之後要去讀 `fsi/async/{id}`
- 這個 id 屬於目前哪個 session
- 這個 job 是哪個 tool 建立的

但這些都沒有結構化 metadata。

### 建議

async tool 回傳值建議改成 JSON，例如：

```json
{
  "asyncId": "...",
  "sessionId": "...",
  "tool": "execute_f_sharp_code_async",
  "submittedAt": "...",
  "statusUri": "fsi/async/..."
}
```

這樣 agent/client 比較容易：

- 記錄
- 回報
- 自動輪詢
- 在 log 中保留可用證據

## 5. 多個 `#r` / `open` 放在同一 block 時，失敗模式不夠可預測

### 問題描述

理論上，agent 會希望這樣做：

1. 一次 reference 一批必要 DLL
2. 一次 open 一批 namespace/module
3. 再進入真正的業務 block

但實務上，本輪最穩的方式反而是：

- 一個一個 `#r`
- 一個一個測 `open`
- 找出哪個 dependency 還沒補上

### 實際範例

一個大 block 失敗時，agent 一開始看不到原因；  
後來拆到最小單位才知道：

- `open Plotly.NET` 是好的
- `open Skender.Stock.Indicators` 是好的
- `open CFar` 是好的
- `open FAkka.TA` 一開始不行，補 `MdcFsClient90.dll` 後才行

換句話說，**工具本身沒有告訴 client 缺哪個 dependency，client 只能手動 bisect**。

### 建議

1. 若某個 `open` 失敗，應回傳缺少的 assembly / namespace resolution 訊息。
2. 若 tool 內部本來就知道目前 loaded assemblies，應直接把「可能缺的依賴」一併提示。
3. 文件中可補一節：對 agent 而言，組裝 session state 的最佳實務是什麼。

## 6. `printfn` / stdout 在 async 結果中不夠可靠，不利於 agent 探測狀態

### 問題描述

agent 常常會用很小的 probe code 來判斷 session 是否準備好了，例如：

```fsharp
printfn "cfar-ready %b root=%s" (cfar.EsMinNk.ContainsKey 30s) root
```

但這類 probe 在 async 結果中，stdout 不一定穩定可見；  
有些情況最後只看到：

```text
val it: unit = ()
```

而看不到 `printfn` 內容。

### 影響

- agent 無法可靠使用 stdout 當健康檢查
- 小型 probe 的可用性下降
- 很多原本可用單行指令確認的事，變成還要再包回傳值或再查 resource

### 建議

1. 明確區分 `fsi-eval result` 與 `stdout/stderr capture`
2. 保證 async 結果內能拿到 `printfn` / `eprintfn` 的輸出
3. 若目前設計上不保證，也請在文件明講

## 7. Path mapping 對 container client 而言不是自描述的

### 問題描述

這個問題比較偏 integration，但它對 agent/client 影響很直接：

- devkit 看到的 `/workspace`
- devkit 看到的 `/gemini4`

和 container 內真正的路徑，並不是 self-describing。

本輪最後整理出的關係是：

- devkit `/workspace` -> container `/workspace/home/devkit_workspace`
- devkit `/gemini4` -> container `/workspace/home`

### 實際範例

要讓 devkit 讀到 container 內的：

```text
/workspace/home/vhdx/cFar_pcsl2/cFar2
```

在 devkit 端其實要改成：

```text
/gemini4/vhdx/cFar_pcsl2/cFar2
```

若這個知識不在文件中，agent 幾乎只能靠 try/error 才能學到。

### 建議

1. 若 server 是部署在帶有 path remap 的環境，建議提供一個 `get_mounts` / `get_workspace_mapping` 類型的能力。
2. 至少在 README / doc 中明確說明常見部署的 path convention。

## 8. 建議新增的工具 / resource

若站在 agent / MCP client 角度，我會優先希望新增這些能力：

1. `get_fsi_session_info`
2. `list_loaded_assemblies`
3. `list_search_paths`
4. `explain_last_error`
5. `load_f_sharp_script_async`
6. `reference_assembly_async`
7. `add_search_path_async`
8. `get_workspace_mapping`

其中最優先的是：

1. `explain_last_error`
2. `get_fsi_session_info`
3. async 版本的 load/reference/search-path

## Bottom Line

這輪的總結很簡單：

- `execute_f_sharp_code_async + fsi/async/{id}` 是正確方向，真的救了長時間初始化 `cfar` 的場景。
- 但若要讓 agent 穩定、低成本地使用，**診斷資訊、session 可觀測性、async 覆蓋率** 還要再補。
- 否則 agent 仍會把大量時間花在「猜 tool 狀態」而不是解決 F# 問題本身。

這些 issue 並不是功能不能用，而是 **對人類手動操作可能還能忍，但對 agent workflow 會明顯放大成本**。
