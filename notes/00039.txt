› 有空(處理完現在在跑的，測試)回答一下:
  不要直接拿 bootstrap/stale proc 的 fsiSupervisorPath 下結論 <= 什麼是 "stale proc 的 fsiSupervisorPath 下結論" ?!


• 意思是：

  - stale proc = 舊的、殘留的 procnode
  - 它可能是前一次測試留下來的
  - 也可能是曾經起來過、後來狀態不乾淨，registry/snapshot 還留著
  - 它對應的 fsiSupervisorPath 也可能還在 GetAllProcInfo 裡出現

  問題是：

  - 你看到 fsiSupervisorPath = akka.tcp://.../user/fsi/supervisor
  - 不代表這個 target 是你現在要驗的那個 fresh host
  - 也不代表它現在的狀態乾淨、可歸因

  所以「拿 stale proc 的 fsiSupervisorPath 下結論」就是：

  - 直接對一個舊 proc 回報的 fsiSupervisorPath 做 GetVesion / ExecCode
  - 然後 timeout 或失敗了
  - 就立刻說「fsi-supervisor 壞了」或「remote host 壞了」

  這個推論不可靠。

  具體例子就是之前的：

  - deploy-startproc-a
  - 或更早的 bootstrap proc

  它們可能：

  - 是舊測試留下的
  - 帶著舊 shard/coordinator 狀態
  - 不是你現在這輪 StartProc 真正新建的 target

  所以正確做法才是：

  1. 先 stop stale proc
  2. 再 StartProc 起一個 fresh procnode
  3. 用 fresh proc 回來的 fsiSupervisorPath
  4. 再測 ListSessions / ExecCode / GetVesion

  這樣失敗了，才比較能說是現在這版程式真的有問題。

• 現在這兩個欄位的定位很清楚：

  - probeMessage
      - ProcSupervisor 對 child proc 做主動健康檢查時，要送的探測指令
      - 例如：listsessions --all true
  - probeIntervalMs
      - 上述探測的週期

  它們不是 create host 的核心必填欄位。
  省略它們的意思只是：

  - host 仍可建立與使用
  - 但 ProcSupervisor 不會幫這個 proc 啟用 active probe

  所以名字看起來重要，沒錯；但它的重要性是「後續 health monitoring」，不是「建立 host 當下的必填前置」。
