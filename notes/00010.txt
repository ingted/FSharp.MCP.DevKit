• 我看完 source、build 過實體專案後，結論是：可以用，而且值得用，但不是「直接整包搬進 FSharp.MCP.DevKit 就好」，而是應該這樣分工。

  - FAkka.FSI.Supervisor
      - 適合當 .NET 10 FSI host 的基底。
      - 它不是單 session toy。現在就已經有 sessionActors 字典、按 session 路由到 FsiWorkerActor，也有 ListSessions、Checkpoint、Fork、Join、ExecBatch。
      - 這跟你要的「一個 host 下多個 session」是對得上的。
  - FAkka.Proc.Supervisor
      - 適合當 proc manager。
      - 它已經有 process snapshot、probe、restart、registry、cluster sharding，責任邊界也合理。
      - 這比我在 FSharp.MCP.DevKit 內自己重做一套 host/process lifecycle 管理更划算。

  所以我的建議是：

  - FSharp.MCP.DevKit 保留 control plane
      - agent registry
      - host registry
      - backward-compatible MCP tools
      - routing / observability
  - FAkka.Proc.Supervisor 負責 host process lifecycle
  - FAkka.FSI.Supervisor 負責 .NET 10 host 內的 multi-session FSI execution
  - .NET Framework host 先沿用現有 FsiHost，之後只補 multi-session 能力

• 有，我也認為這裡要再精煉一下，而且我傾向是：

  不要把 routing/trace metadata 直接塞進裸的 FsiResult，而是拆成兩層。

  建議改成：

  - FsiResult
      - Output
      - Errors
      - IsSuccess
      - ExecutionTime
      - Diagnostics
      - Value option
      - RawErrorType option
  - FsiExecutionRecord 或 FsiExecutionEnvelope
      - ResultId
      - RequestId
      - AgentId
      - BackendKind
      - HostId
      - SessionId
      - SubmittedAt
      - StartedAt
      - CompletedAt
      - Result : FsiResult

  原因：

  1. FsiResult 應該代表「一次 FSI 執行的語意結果」，不是 routing 容器。
  2. backendKind/hostId/sessionId/resultId 是 traceability / observability metadata，和 result payload 是不同層次。
  3. 如果全部塞進 FsiResult，之後做集合運算、相等性、cache key、序列化都會變髒。

  所以你提的欄位我贊成加，但我會加在 FsiExecutionRecord，不是裸 FsiResult。

  你問的 quotation / 集合運算，我也覺得值得做，但我不建議第一版就直接把真正的 F# quotation object 當 MCP payload 傳。那會有三個問題：

  1. transport 很醜，<@ ... @> 本質上還是要變字串/JSON
  2. cross-runtime 相容性差
  3. 安全面和錯誤診斷會很難收斂

  我建議分兩階段：

  1. 先做 result registry
      - 每次 execution 產生 ResultId
      - 可 get/list/query result records
  2. 再做 server-side result query
      - 先收 quotationText: string 或 queryCode: string
      - server 在專用 analysis session 內執行
      - 輸入不是隨意環境，而是明確提供：
          - recordSeq : FsiExecutionRecord seq
          - resultSeq : FsiResult seq

  這樣你要的這類能力就能成立：

  - 單筆：
      - 比較兩次 execution 的 Output/Errors/Diagnostics/Value
  - 雙集合：
      - exists
      - forall
      - map
      - filter
      - zip
      - groupBy
      - diff
  - 例如概念上：
      - forAllFsiResult opQuot ridSeq1 ridSeq2
      - mapFsiExecutionRecord opQuot ridSeq
      - compareFsiResults rid1 rid2

  我會把它設計成：

  - ResultId 是主鍵
  - quotation/query 只吃 ResultId seq
  - server 先把 ResultId seq -> FsiExecutionRecord seq
  - 再做 query evaluation

  這樣 agent 的操作就會很乾淨，而且不需要自己保存整包 result payload。

  我的結論是：

  - ResultId 要有
  - backendKind/hostId/sessionId 要有
  - 但它們應該進 FsiExecutionRecord
  - FsiResult 保持純 payload
  - quotation/result-set ops 值得做，但應作為第二層 query capability，不要直接污染 execution contract

  如果你同意，我會先把這個修正回寫到 SD.md，再進 WBS。
