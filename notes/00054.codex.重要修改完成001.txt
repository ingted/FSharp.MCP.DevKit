• 意思很直接：

  execute_f_sharp_code_async_routed 跟 execute_f_sharp_code_routed 執行的還是同一個 remote host、同一個 remote session。
  不是換一個 session，也不是換一套語意。

  差異只有控制流程：

  - execute_f_sharp_code_routed
      - 你送 code 之後，caller 會同步等到整段 code 執行完才拿回結果
      - 對短 snippet 很方便
      - 但對長腳本，現在 live 上已實測會比較容易在這條同步等待路徑上出現：
          - AskTimeoutException
          - EndpointDisassociatedException
  - execute_f_sharp_code_async_routed
      - 你送 code 後，只是先把工作排進去，立刻拿到 asyncId
      - 然後用 fsi/async/{asyncId} 輪詢
      - 等它真的完成後，再在同一個 session 做 evaluate_f_sharp_expression_routed

  所以我說的：

  > 真實業務腳本一律優先 execute_f_sharp_code_async_routed，完成後再 evaluate_f_sharp_expression_routed

  白話就是：

  1. 先把重腳本在該 session 裡跑完
  2. 不要同步卡死在單次 ask 上
  3. 確認 async 完成後
  4. 再在同一 session 讀你要的變數/表達式值

  為什麼這樣做：

  - 目前已知脆弱的是「長時間同步等待」這條路
  - 不是 remote session binding 本身
  - 所以 async-first 是避開同步控制路徑的穩定性問題
  - 不是 workaround 成另一種執行語意

  - sync / async 的執行結果語意應該一樣
  - 差別在「你是同步等整段跑完」，還是「先排進去、稍後輪詢完成」
  - 現在對長腳本，後者比較穩
