› /send 是 fsi supervisor 的 api 還是 proc supervisor?

  具體是：

  - endpoint 定義在 /workspace/home/work/PulseTrade.fs/Libs/Akka.Proc.Supervisor/ProcRest.fs
  - 路徑是：
      - POST /api/proc/nodes/{procId}/send

  但它的作用不是自己執行 F#，而是：

  1. ProcSupervisor 收到 /send
  2. 轉成 ForwardMessage
  3. forward 到指定 procId 對應的 procnode
  4. procnode 再把訊息送進它內嵌的 Akka.FSI.Supervisor
  5. Akka.FSI.Supervisor 執行後回傳 ExecResult
  6. ProcSupervisor 再把結果回成 HTTP JSON

  所以關係是：

  - /send 這個 API surface：ProcSupervisor
  - 真正執行 F# code：FSI Supervisor

  也因此現在的 bug 才會看起來像兩邊交界問題：

  - API 在 ProcSupervisor
  - 但壞 payload 來源大概率是 FSI Supervisor 回來的錯誤物件

• 是，從目前程式碼看，/send 的原始設計就是綁 FSI supervisor 的，不是泛用 arbitrary process messaging API。

  證據很直接：

  - ProcRest.fs 把 /api/proc/nodes/{procId}/send 轉成 ForwardMessage
  - ProcSupervisor.fs 收到 ForwardMessage 之後，不是送去子 process stdin，也不是 generic RPC
  - 它會：
      1. 用 ProcMessageParser.tryParse 把字串解析成 FSI contract message
      2. 再 forwardToFsi
      3. target 就是 fsiSupervisorPath

  程式裡甚至直接寫了這句註解：

  - /workspace/home/work/PulseTrade.fs/Libs/Akka.Proc.Supervisor/ProcSupervisor.fs:317
      - ForwardMessage is routed ... then forwarded to the FSI supervisor

  而且 ProcNodeReady 契約本身也長這樣：

  - /workspace/home/work/PulseTrade.fs/Libs/Akka.Proc.Supervisor/ProcContracts.fs:12
      - fsiSupervisorPath: string

  也就是說，ProcSupervisor 預期每個被管理的 procnode 都會回報一個 fsiSupervisorPath。
  沒有這個 path，ForwardMessage 就直接回：

  - FSI supervisor not ready.

  所以對你問的這句：

  > 假設我起的不是 fsi supervisor process 那麼 /send 到底是啥?

  答案是：

  - 照目前原始設計，它就沒有泛用意義
  - 如果你起的不是內嵌 FSI supervisor 的 process，/send 基本上就不成立
  - 最多只會變成：
      - procnode 活著
      - 但沒有 fsiSupervisorPath
      - 然後 /send 回 FSI supervisor not ready.

  所以這個 API 的本意其實是：

  - ProcSupervisor = process lifecycle + routing shell
  - /send = 專門給「內嵌 FSI supervisor 的 procnode」轉送 FSI 指令

  不是：

  - 通用 process command bus
  - 通用 actor message tunnel
  - 任意 child process 的 stdin 控制面

  如果要支援「不是 FSI supervisor 的 process 也能被 /send」，那會需要重新定義 API，例如分成：

  - /send-fsi
  - /signal
  - /stdin
  - /rpc

  現在這份設計沒有做到這層抽象。


› 但是假設一開始的設計就是不指定啟動的 dll / exe 檔，那麼就是"起動成為 fsi supervisor host" 對吧?


• 對，如果你指的是原始設計裡的「不指定自訂 dll/exe，直接走預設啟動」，那它的意圖就是：

  - 啟動一個 內建 FSI supervisor 的 procnode host

  也就是 /workspace/home/work/PulseTrade.fs/Libs/Akka.Proc.Supervisor/README.md 裡的：

  - POST /api/proc/nodes/start-default

  這條路不是 generic process start。它本質上是：

  1. ProcSupervisor 啟動「同一支 Akka.Proc.Supervisor 程式」
  2. 但加上 --mode procnode
  3. 這個 procnode 啟來後會內建 Akka.FSI.Supervisor
  4. 然後回報 fsiSupervisorPath
  5. 之後 /send 才有意義

  所以：

  - start-default 的語意：起一個 FSI host
  - /send 的語意：送 FSI 指令到那個 host

  只有這條才是原設計的閉環。

  相對地：

  - POST /api/proc/nodes/start

  這條才是「你可以指定任意 fileName + args」的 custom process start。
  但如果你啟的不是會回報 fsiSupervisorPath 的東西，那它雖然仍可被 ProcSupervisor 管 lifecycle，卻不是 /send 的合法目標。

  所以可以把原始設計理解成兩層：

  - ProcSupervisor 本體：可管 generic OS process
  - /send 這個 API：只對「被設計成 FSI host 的 procnode」成立

  你這樣理解是對的。
