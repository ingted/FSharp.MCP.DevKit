› 為什麼要 smoke 啊?


• 因為這一輪改的是控制面和路由，不是單一純函式。

  單元測試能證明：

  - 某個 adapter 會不會 map 對
  - 某個 registry 會不會存對
  - 某個 query service 會不會算對

  但它不保證這些東西串起來後還對。這次風險最大的地方其實是「串接」：

  - 舊工具是不是還走得到 default route
  - 顯式 agentId/hostId/sessionId 是不是真的一路帶到 backend
  - 多 host / 多 session 狀態會不會互相污染
  - async queue 的順序和 asyncId -> ResultId linkage 有沒有斷
  - result plane 從 execution record 到 query/materialization 能不能接起來

  這些都不是單一 module 的責任，所以要有 smoke。

  我這裡說的 smoke，不是大型 e2e 壓測，而是最低限度的高階回歸：

  - 用最短路徑確認主線真的通
  - 專門抓「每個零件都對，但串起來壞掉」這種問題

  如果不做 smoke，這次很容易出現：

  - WBS 看起來很多 done
  - 單元測試也都綠
  - 但實際 agent 用起來在 control-plane / route / result-plane 的交界處壞掉

  所以 smoke 的目的不是取代單元測試，而是補 integration gap。
  如果你覺得名稱不精準，也可以把它理解成「高階回歸測試」。
